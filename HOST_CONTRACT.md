# Host contract — what the Max It host actually does

The plugins a mini-program reaches through `wx.invokeNativePlugin`, as **observed** in production mini-programs (2025–2026). This is the SDK's source of truth and the document the host team is asked to confirm or correct. Every entry says what was seen, not what was promised.

## Envelope

A success answers through `success(res)` with:

```json
{ "result": "success", "status_code": 200, "data": { … } }
```

A **failure may also come through `success`**, with a failure envelope (`result: "fail"`, a `status_code`, a `message`, and sometimes extra fields such as `txnid`). The `fail(err)` callback carries `{ errMsg }` and is used for runtime-level refusals (unknown API, cancelled sheet, denied permission). The SDK treats both roads the same way and keeps the raw payload on `HostError.raw`.

Plugins are **not ready the instant the app launches**: the first `userInfos` or `login` can fail for a few hundred milliseconds. The SDK waits and retries.

## `userInfos`

- Request: `{}`.
- Answer: `data.user = { msisdn, firstName, lastName, … }`.
- Observed: the msisdn arrives **as the subscriber registered it** — `+221 77…`, `221 77…`, `00221…`, with spaces. `firstName`/`lastName` may be missing, and a missing one has been seen serialised as the string `"undefined"`. Backends that validate the msisdn at nine characters answered a bare 400 to a share of real users (stadium, 2026-10-28). The SDK normalises both.

## `login`

- Request: `{}`.
- Answer: `data.code` (seen at top level as `code` on some builds): a one-time code, exchanged by the app against `POST {GATEWAY_URL}/auth/session { code, appId }` on the mini-app auth broker. No client secret is involved.

## `merchantPay`

- Request:

| Field                               | Type   | Note                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `amount`                            | number | XOF                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `receiver`                          | number | the **merchant code** (the account the money lands on), never the msisdn, never 0                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `receiverName`                      | string | merchant display name                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `orderDescription`, `message`       | string | what the customer reads on the sheet (both names have been used; the SDK sends both)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `orderId`                           | string | the app's order id                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `idService` **and** `serviceId`     | string | the correlation key the host records on the debit (the exact-match key for a later verification) — **ONE value, sent under BOTH names since SDK 0.1.5.** The host source on disk (samea-mobile `MiniAppPayReq.fromMap`, 2026-10-21 build, read 2026-10-30 and again 2026-11-03) reads `idService` and forwards it as `serviceId` in its `/omy/secure-pay-merchand` body; which spelling the build in customers' hands reads cannot be known from a mini-program, and BRT — the one app whose key is proven in the Orange Money ledger (txn-verify DOMAIN-KNOWLEDGE §3) — has always sent both. « The host refuses the pair » (SDK 0.1.0 → 0.1.4) was wrong: nothing in the host's code refuses it. |
| `reference`                         | string | copied by the host into the debit's metadata                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `payload`                           | object | `{ nom_marchand, code_marchand, reference }` — the block the host reads the merchant and the reference from. A **replace, not a merge**, on the native side: send it whole.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `currency`                          | string | `XOF`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `customerMsisdn`                    | string | optional                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `merchantMsisdn`, `fees`, `appInfo` | —      | older fields some apps still send; tolerated, not required (pass them through `extra` if your backend reads them)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

- Observed: `amount` has been accepted both as a number and as a string.

- Answer: `data.txnid` — also seen as `trxReference`, `transactionId`, `reference`.
- **Identical transaction.** The host refuses a second identical payment (same payer, merchant, amount) for about 15 minutes with a `success` failure envelope whose message ends in « … continuer ? » (variants: « identique », « similaire », « même transaction ») and which **carries a `txnid`** at the top level of the envelope. To proceed, the app calls `merchantPay` again with the same payload plus `txnid` and **`caction: '1'` — a string**: the host's typed request has `caction` as a nullable string and a number fails its type check before the payment runs (fixed in production 2026-10-24).
- Observed: when the error string carries no id, the host has put the **whole message** in `txnid` (`CODE:2040;MESSAGE:…;TXNID:null`) or the literal `"null"`. The SDK refuses those as ids.
- A 0 F amount is refused by the host with a message the decline patterns do not know. Do not send free items through the sheet.
- After a `TIMEOUT` or an unnamed failure the debit **may have happened**: the SDK marks the error `uncertain`. An app that sells things needs a verification step before letting the user pay again (the fleet uses the txn-verify oracle on the mini-app gateway).

### What the host does while a payment runs (read in samea-mobile, 2026-11-03)

`_handleMerchantPay` brings the HOST's activity to the front (`moveFlutterToFront`), shows its resume sheet (`miniAppResume`, `showResumeModal`), asks the PIN (`UIHelper.withValidPin`), calls Orange Money (`securePayMerchand`), then `backToMM(call)` = `moveMiniAppToFront(appId)` and returns the answer. On Android the mini-program runs in **its own process (`:mini1`…`:mini5`) and its own task**; the call reached the host through the TMF IPC (`callMainProcessPlugin`, `FlutterMethodCallIPCPlugin`), and the answer goes back through the SAME one-shot IPC callback, bound to that process. The whole time the mini-program's process is a background process of the app with no foreground component. **If the OS kills it meanwhile** (low memory, an OEM battery manager — Tecno/Infinix/Xiaomi are the usual suspects), the answer has no receiver, `moveMiniAppToFront` brings back an EMPTY task and TCMPP starts the mini-program COLD: no `success` callback, no `fail`, no launch params — « the host opens the mini-program again and nothing arrives ». The host keeps NO durable record of a result it could not deliver; it only logs the success to analytics.

What follows for a mini-program: the debt record must exist BEFORE the call (then a cold start finds it and can ask the oracle, which is what `checkout.js` in mp-events does), and nothing can be waited on across a process death. The fix that belongs to the host is open question 5.

## `transfertMoney`

Person-to-person Orange Money transfer. Read in the host's source (samea-mobile `_handleTransfert` / `_processTransfert`, 2026-11-22); not yet observed on a device through the SDK.

- Request: `{ receiver, amount }` — the only two fields the host requires (`MiniAppPayReq.isValid`). `receiverName` and `message` are read for its summary sheet.
- **The sender is not the app's to say.** The host debits its own session's subscriber (`store.data['msisdn']`); a `sender` in the request is parsed and never used.
- **The fees are not the app's to say either.** The host computes fees and tax for the amount (`getFees`, tariff `P2P`) and overwrites whatever the request carried, then shows them on its summary. An app cannot promise « sans frais ».
- Flow: the host comes to the front, shows its summary, asks the PIN, calls Orange Money, returns to the mini-program. A wrong PIN is asked again inside the host and never reaches the app.
- Answer on success: `data = { code: "SUCCEED", sender, firstName, lastName, txnid, amount }`. `txnid` is whatever Orange Money returned and **may be null**.
- Refusals, all through `success` with `{ status_code: 400, result: "fail", message }`:
  - « Input body » — receiver or amount missing.
  - « User cancelled » — the user closed the summary. **Also what the host answers when its own summary step throws**, so it is not proof of a deliberate cancel; either way nothing was debited.
  - « Pin is required » — the PIN pad was closed empty. Nothing debited.
  - anything else — Orange Money's own message for the failed transfer (balance, limits, network).
- Like `merchantPay`, the mini-program's process can die while the host is in front: after a `TIMEOUT` or an unnamed failure the debit **may have happened**.

## `contactList`

- Request: **none** — the plugin answers an empty list when handed a `data` field (observed 2026-10).
- Answer: seen as `{ data: { contacts } }`, `{ contacts }` and `{ data: [ … ] }`. Each contact: `{ name, msisdn }` with `msisdn` a string or an array of strings.
- A refused permission arrives through `fail` with an `auth deny`-style message.

## `share`

Read in the host's source (samea-mobile `_handleShareElement`, 2026-11-22). **Not wrapped by the SDK**: no app of the fleet needs it through the SDK yet.

- Request: `{ shareFile, message }`. `shareFile` is **required** and must be a `data:` URI of an image: the host decodes it, writes a temporary `.jpg` and opens the system share sheet with that file and `message` as its text. `message` defaults to « Partage de reçu ✅ ».
- **There is no text-only share.** Without a `shareFile` the handler throws on parsing and answers « Échec du partage: … ». An app that wants to share a link or a code must render it into an image first.
- `appInfo`, which older apps send, is not read.
- Answer: `data = { message: "Partage effectué avec succès" }` as soon as the sheet was opened; the host cannot tell whether the user actually sent anything.

## `block_screen`

- Request: `{ activate: true | false }`.
- Effect: masks the screen in captures on **iOS**, where the runtime's `wx.setVisualEffectOnCapture` masks nothing. **Host-wide**: it does not lift itself when the view closes; `false` must be called. On Android the runtime call works (`FLAG_SECURE`).

## `getDeeplinkParams`

- Request: `{}`.
- Answer: `data.params` — the map of everything after the « ? » of the URL the host opened the mini-program from (`https://<host>/mini-apps/<appId>?a=b`). **One-shot**: the host clears its copy once read. `null`/absent when nothing is pending.
- Observed: links are also issued in a **slash form** (`…/mini-apps/<appId>/a=b&c=d`). The host's router captures `:id` with `.*`, so the tail arrives glued to the app id, as one key or one value. The SDK expands both.
- The launch options' `query` is a second source (DevTools compile condition). The host's wins.
- **Since 2026-10-30 the host starts the mini-program with TCMPP `MiniStartOptions.params`** — a STRING (the link's tail, issued as `https://<host>/miniapps/<appId>??a=b&c=d`, TWO question marks) that the runtime hands to `App.onLaunch`/`onShow` as **`options.referrerInfo.extraData`** (and `options.extendData`), not as `options.query` (TCMPP « Basic » doc, getLaunchOptionsSync: Android `extraData` = `MiniStartOptions.params`, iOS = `paramsStr`). Pass the WHOLE options object to `deeplink({launch})`; the SDK reads `path?…` → `query` → `extraData` → `extendData` and strips the stray `?` from keys. ⚠ `onShow` repeats the same options on every resume; the SDK now handles this itself — `deeplink()` is one-shot by default (it fingerprints the resolved params and answers `null` for a repeat), so calling it on every `onShow` no longer re-routes on an app switch. Pass `{once: false}` to opt out.

## Not plugins, but handled

- `wx.scanCode` — `onlyFromCamera` is honoured; a host that cannot open the camera-only variant fails with a generic message, and the SDK retries with the album allowed, flagged.
- `wx.setVisualEffectOnCapture` — Android only in practice.

4. ~~Whether the slash-form deep link will be parsed host-side~~ — superseded 2026-10-30 by `MiniStartOptions.params`; is `getDeeplinkParams` still populated by the new build, or is the launch-options door now the only one?
5. **A payment result that survives the mini-program's death** (2026-11-03). When `merchantPay` completes and the mini-program's process is gone, the answer is lost (see « What the host does while a payment runs »). Ask: keep the result in the main process keyed by `appId` (+ `idService`/`reference`), like `_pendingDeeplinkParams`, and hand it over at the next launch of that app — on the launch options (`MiniStartOptions.params`, e.g. `payment=<txnid>&idService=…`) or through a `getPendingPaymentResult` plugin the SDK would call on `onShow`, one-shot. Until then every mini-program must treat a cold start after a payment as « maybe debited » and verify.

6. **The payment's correlation fields, host side (read 2026-11-03, `_processMerchantPayment` + `_logPaymentSuccess`).** What the host forwards to `/omy/secure-pay-merchand`: `serviceId: params.idService ?? ''`, `metadata.reference: params.reference` — and `payload.reference` **only on the identical-transaction retry branch** (`caction` set); the first attempt's `payload` is `{nom_marchand, code_marchand}` without the reference. The analytics event `make_mini_app_payment` carries amount · receiver · receiverName · app name/version/id and **neither `idService` nor `reference`** — if « the backend log » is that event, the fields are missing by construction, not because the mini-program omitted them. Field names vs the backend's published schema (`SecurePayMerchantReq`): the host sends `txnid` where the schema says `txnId`, `versionApp` where it says `appVersion`, and `serviceId` / `payload` which the schema does not list at all (the backend evidently maps `serviceId` into the ledger payload's slot, since BRT's shows up there). Asks: put `reference` in `payload` on both branches; add `idService` + `reference` to the two analytics events; align the casing with the schema or fix the schema.

7. **« Unregistered event » on every plugin call — the TCMPP bridge hijacked by the Firebase background engine (read 2026-11-10, Android).** Symptom on real phones, production and sandbox, same Max It version: every `wx.invokeNativePlugin` (`userInfos`, `login`, …) answers `invokeNativePlugin:fail Unregistered event` for the whole mini-program session; other phones on the same version are fine; the released build sells at 450 tickets/hour meanwhile. The chain, in the sources on disk: the mini-program's process → `DummyJSPlugin.onInterceptJsEvent` → `FlutterMethodCaller.callFlutter("jsEvent")` → IPC to the main process (`FlutterMethodCallIPCPlugin`) → `callFlutterInternal` → `mMethodChannel.invokeMethod` → Dart `_handleMethod` → `_miniApiHandlers[apiName]`. « Unregistered event » is the SDK's wording for Flutter's `notImplemented`, which the engine answers when **no Dart handler is installed on the channel of the engine the call reached**. `FlutterMethodCaller` is a singleton holding ONE channel, bound by `TcmppFlutterPlugin.onAttachedToEngine` — i.e. by _whichever Flutter engine attached last_. The host registers `FirebaseMessaging.onBackgroundMessage` (`main.dart`): on Android, a push received while Max It is not foreground — and **the host IS background while a mini-program's own process is on screen**, e.g. the « paiement réussi » push of the ticket just bought — makes `firebase_messaging` create a second `FlutterEngine` in the main process (`FlutterFirebaseMessagingBackgroundExecutor.startBackgroundIsolate`, kept alive afterwards); Flutter's automatic plugin registration attaches `tcmpp_flutter` to it, `bindMethodChannel` rebinds the singleton to that engine, whose isolate never constructs `TcmppFlutter()` and so has no `jsEvent` handler. From that moment every mini-program call on the phone is « Unregistered event », until the host's main engine attaches again (a full restart of Max It). Fix options, host side: (a) in a forked/patched `TcmppFlutterPlugin.onAttachedToEngine`, bind only the first (main) engine, or re-bind to the main engine when it resumes; (b) make the background isolate harmless — in the `onBackgroundMessage` handler construct nothing TCMPP, and ask Tencent for a guard in the plugin; (c) at least, on `AppLifecycleState.resumed` of the main engine, re-register (`MiniAppService.initializeApp()` with `initialized` reset) — it does not rebind the native singleton, so (a) is the real fix. Mini-program side there is no recovery: the SDK now reports the host's words (`HostError.hostMessage`) and the apps tell the user to close Max It completely and reopen it.
